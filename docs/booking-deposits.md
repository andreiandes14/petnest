# Booking deposits (PayMongo test mode)

Attendance policy version 2: a paid deposit is a service credit, not an extra service fee. Confirming Completed persists depositDisposition=credited, depositCreditedAt and price-minus-50 as the remaining balance, without marking that balance collected. Confirming No-Show after the Philippine appointment start persists depositDisposition=forfeited, noShowAt, noShowProviderId, noShowMarkedByUserId and remainingServiceBalance=0. Existing PayMongo payment fields remain untouched. Terminal-state compare-and-set prevents duplicate attendance transitions and cross-transitions. Existing No-Show records also display no balance due through the shared balance helper; historical records are not bulk-modified. Retention under the booking agreement does not establish that PayMongo has settled or transferred funds to a provider.

New grooming/vaccination bookings require acknowledgment of the shared PHP 50 deposit policy. Services priced below PHP 50 cannot be booked through this flow; the customer must contact the provider. Legacy bookings have no depositRequired flag and retain their existing behavior. Manual history records never create a payment.

The provider acceptance endpoint stores awaiting_payment for new bookings. Only a verified paid webhook or authenticated server-to-server PayMongo session reconciliation can move these bookings to confirmed. Booking payment fields live on the booking, with unique PETNEST-BOOKING references and petnest_booking_id metadata, distinct from supply orders. A small repository adapter reuses the existing PayMongo checkout, test-key enforcement, raw-body signature verification, amount/method checks, atomic attempt lock, and notification retry logic. Supply orders continue charging their actual snapshot totals.

POST /api/bookings/:bookingId/payment requires the owning customer and an accepted unpaid booking. Return URLs use the existing server-side APP_URL and /bookings; return query parameters are never payment proof. Keep the existing /api/webhooks/paymongo endpoint and checkout_session.payment.paid subscription. No new secrets, webhook configuration, jobs, or live payments are introduced.

After verification, the server stores the PHP 50 paid amount, payment reference, timestamp, and remaining balance derived from the original booking price. The service price is unchanged; the outstanding balance is collected directly by the provider.

No-Show is an explicit provider action requiring confirmation of absence without prior notice. The backend checks provider ownership, confirmed/paid state, scheduled time in Philippine time, and an atomic previous-state match. Records with prior cancellation notice cannot use this forfeiture action. No-Show timestamps and deposit forfeiture timestamps preserve history; cancellation/refund policies are not automated. Existing cancellation and refund situations require their separate policy.

Validation uses synthetic keys, mocked PayMongo responses and isolated repositories. Tests do not load credentials, call PayMongo, or modify real bookings. Run node --test --test-isolation=none apps/api/tests/booking-payments.test.mjs apps/api/tests/paymongo.test.mjs and node scripts/check-vaccination-followup.mjs, plus pnpm run build.

## Missed webhook recovery

POST /api/bookings/:bookingId/payment/verify requires the owning authenticated customer. It retrieves only the session ID already stored on that booking using the server test key and PayMongo's documented GET /v1/checkout_sessions/{id}. It requires matching session ID, attempt reference and test mode, then passes successful payments through the same amount/currency/method/metadata and atomic persistence checks as the signed webhook. Return URL parameters never authorize a paid transition. Webhook HMAC checks remain unchanged.

Customer booking cards with active or uncertain attempts verify immediately and every 10 seconds for up to two minutes (including after returning from checkout). They show a verification state, refresh persisted bookings, stop when paid/unmounted, and explain delayed confirmation rather than claiming payment failed. Existing sessions are also verified before checkout reuse; no new charge is created by verification. Customer/provider panels share the persisted booking and balance calculation.

Investigation on October 16, 2026 found booking #44 unpaid in MongoDB despite a matching successful PHP 50 test session. The expected public webhook was enabled, subscribed to checkout paid events, reachable, and its signing secret matched the local configuration. Original delivery logs were unavailable, so the precise historical delivery/rejection cause could not be established. After the recovery implementation, booking #44 persisted confirmed/PAID, deposit 50, remaining balance 950, notifications SENT; the customer page displayed these values with no payment button. No additional checkout was created.
